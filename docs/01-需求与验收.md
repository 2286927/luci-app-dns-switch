# luci-app-dns-switch 需求重写 v2

> 起因：v1 做成了「两个按钮 + 一张状态表」。能跑，但它是个**给作者自己用的工具**，不是产品。
> 本文从领域里最原始的场景反推，重写需求。

---

## 零、一处更正（2026-11-09 20:10）

初稿把「上午整网失联」当成了 DNS 改坏的案例，据此推出 S1。**这个因果关系是错的。**

真实原因见 `dns-arch-20261109/DNS改动清单与维护指南.md` 第 5 行与 `.workbuddy/memory/2026-11-03.md`「network restart 卡死根因」：用户在 LuCI「启动项」里重启 Internet 接口，触发 **netifd 对 ubus 无响应**，`ifdown -a` 逐条超时，所有接口被拆掉后不再重建，netlink 层一并卡死（`ip` 命令本身挂住），而脚本仍返回 `rc=0`，LuCI 显示成功。这与 DNS 配置无关。

这个更正改变了两件事：

1. **失联分两种，不能用同一套办法救。** DNS 层的失联和网络服务层的失联是不同故障域。
2. **`rescue` 的适用边界必须写死。** 它只管 DNS，撞上 netifd 卡死时它做不了任何事，而且不该冒充能救。

## 一、先纠正定位

v1 的隐含假设是「用户想切换 DNS」。

真实假设应该是：**用户的网络刚才坏过，他怕再坏，而且他不确定现在到底好不好。**

所以产品不是「DNS 开关」，是**「家庭 DNS 的可用性管家」**。开关只是它其中一个动作。

判断标准变了：

| v1 的标准 | v2 的标准 |
|---|---|
| 能一键切过去 | 切过去之后，**DNS 出任何事都能在 90 秒内回到能解析的状态**（接口层故障不在此列，也不许冒充能救） |
| 状态显示正确 | 状态**持续对账**，被改坏了自己修回来并说明原因 |
| 有日志 | 有**可交付给他人的诊断包** |
| 作者看得懂 | **完全不懂 DNS 的人**看得懂第一屏 |

## 二、原始场景（Jobs To Be Done）

不是访谈出来的假需求，是从真实故障里提炼的。

### S1 失联急救（最高优先级）

先把故障域分开，混在一起设计出来的东西两头不讨好。

| 故障域 | 典型表现 | 该谁负责 | dns-switch 能做什么 |
|---|---|---|---|
| **F1 DNS 层** | 网页打不开但 `ping 223.5.5.5` 通；`nslookup` 超时或报 SERVFAIL | dns-switch | **全部**。切回原生、换上游、清劫持，一条命令 |
| **F2 网络服务层** | `ping 网关` 不通，连 LAN 地址都丢；`ip addr` 命令挂住 | netifd / 内核，`netguard` 兜底 | **什么都做不了**，也不该尝试 |

> F2 的真实案例：重启 Internet 接口 → netifd 对 ubus 无响应 → 接口全拆不重建 → 整机失联 8 小时，靠断电恢复。已装 `netguard`（`ping` 探活，不走 netlink，LAN 丢地址 5 分钟即 `reboot -f`）兜底。

所以 S1 收敛成一句话：**「我改错了 DNS，怎么在 60 秒内让全屋重新能上网，而不需要重新登录路由器。」**

关键约束三条：

1. 急救动作**不能依赖浏览器**，也不能依赖 DNS 本身解析成功。
2. **不能依赖 daemon 在跑**——daemon 可能正是被改坏的那一环。
3. **不能和 netguard 抢决策**。netguard 判断的是「要不要重启整机」，dns-switch 判断的是「DNS 配置要不要回滚」。后者永远不重启、不碰接口，越界会掩盖真正的故障，也会让 netguard 的判据失真。

→ 交付一条纯 sh 的 `dns-switch rescue`，不读 uci、不解析 nft、不调其他函数，只做「把 dnsmasq 拉回原生 + 重启 + 打印结果」。

### S2 状态漂移

> 「上个月配好的，今天发现孩子又能刷短视频了。」

漂移来源：固件升级、断电、他人改 LuCI、别的插件抢 53、ADH 自己更新后端口变。
→ 需要「期望状态」持久化 + 周期性对账 + **漂移发生时留下时间线和原因**。

### S3 看不懂

> 截图里框出来的 ADH 地址、当前上游、MAC、853 说明。

这些是证据，不是结论。用户要的是「现在好不好、坏了怎么办」，不是「240e:9:2000:100:...」。
→ 信息分层：默认给人话，证据折叠。

### S4 新设备不听话

> 「新买的电视盒子自己用 8.8.8.8，广告还是照弹。」

→ 需要「哪些设备绕过了」的可见性（ADH 查询日志里能看出），而不是只做全量劫持。

### S5 向别人证明它在起作用

> 「我老婆说这玩意儿没用，网还变慢了。」

→ 需要可展示的效果数据：拦截量、平均解析耗时、降级次数。

## 三、需求分层

### P0（没有就不算产品）

| 编号 | 需求 | 可执行验收 |
|---|---|---|
| P0-1 | 急救通道：`dns-switch rescue` 一行命令把 DNS 复位到原生，不依赖 daemon、不依赖 LuCI、不读 uci、不解析 nft；**永不重启、永不碰网络接口** | 停掉 daemon 后执行，退出码 0，`nslookup 127.0.0.1` 成功；复位后仍失败时必须打印「DNS 已复位但仍不可用，可能是接口/网络服务问题，看 netguard」，不得假装成功 |
| P0-2 | 切换事务化：改前快照、改后自检、失败自动回滚 | 把 ADH 地址改成黑洞，`on` 返回非 0，`/etc/config/dhcp` 的 md5 不变 |
| P0-3 | 持续对账：55 秒一轮，漂移自动修复并记录原因 | 手工 `uci delete dhcp.@dnsmasq[0].server`，120 秒内被自动补回 |
| P0-4 | 默认视图人话化：三行结论，技术细节折叠 | 首屏不含 IP、MAC、十六进制地址 |
| P0-5 | 冲突检测：启动时识别抢占 53 的插件并明确报错 | 手动把 dnsmasq 端口改 1745，页面与 `status` 均报「被 X 占用」 | ✅ 2026-11-10 已完成，见 `README.md`「P0-5」与 `测试报告-P0-5.md` |
| P0-6 | 演练：`dns-switch drill` 主动验证降级链 | 执行后返回 0，时间线里留下一次 drill 记录 |

### P1（决定它是否好用）

| 编号 | 需求 | 说明 |
|---|---|---|
| P1-1 | 诊断包 `dns-switch bundle` | 打包 nft 规则、uci 相关段、conntrack 采样、解析结果、dmesg 尾部，输出单个 tar.gz 路径 |
| P1-2 | 快照与回滚 | 保留最近 N 份，`snapshot list/diff/restore` |
| P1-3 | 上游链抽象 | 有序列表 + 每级独立探测 + 手动锁定某级，而不是硬编码「ADH + 运营商」 |
| P1-4 | 时间线 | 最近 7 天的切换/降级/漂移事件，带原因 |
| P1-5 | 效果统计 | 拦截量、降级次数、平均解析耗时 |
| P1-6 | 审计 | 谁切的、来源 IP、时间 |

### P2（生态与工程）

| 编号 | 需求 |
|---|---|
| P2-1 | ubus 对象 `dns-switch`，LuCI 只是客户端之一；提供 `status --json` |
| P2-2 | 配置导入导出（YAML），便于备份与社区分享 |
| P2-3 | 三档预设模板（简单 / 家庭 / 进阶），每档只暴露必要字段 |
| P2-4 | i18n（中英），术语平民化 |
| P2-5 | QEMU 回归：CI 里跑 x86 ImmortalWrt，`uci set` + 断言脚本 |
| P2-6 | 兼容性矩阵：明确支持哪些固件版本、哪些 DNS 后端 |

### 明确不做

| 不做 | 原因 | 何时再说 |
|---|---|---|
| **修 netifd 卡死 / 接口重启后不重建** | 这是网络服务层的内核/守护进程缺陷，属于另一个项目；本应用越界接管只会掩盖真故障，还会干扰 `netguard` 的 reboot 判据 | 单独立项，见 `dns-arch` 与 netguard 记录 |
| 内置 DNS 服务器 | ADH/mosdns/smartdns 已经够多，不该再造一个 | 永不做 |
| 按客户端分流策略 | 需要 VLAN/策略路由配合，家庭场景收益低、复杂度高 | 有明确诉求时单独立项 |
| 云端配置同步 | 隐私与自建成本 | 不做 |
| 自动升级 DNS 二进制 | 与现有值守升级冲突 | 不做 |

## 五、技术路线调整

### 5.1 后端从 shell 迁到 ucode

现状是 793 行 POSIX sh。能跑，但：

- 状态机、JSON、错误处理在 shell 里都是硬凑
- OpenWrt 25.12 已经是 ucode 运行时，LuCI 本身也是 ucode
- 无法做单元测试

建议：核心逻辑用 ucode 重写，`/usr/libexec/rpcd/dns-switch` 暴露 ubus 对象。shell 只保留 `rescue` 这一条**不能依赖任何东西**的逃生命令。

代价是重写。收益是可测、可维护、可被第三方调用。

### 5.2 IPC 从「uci 当通道」改成 rpcd + ACL

v1 用 uci + `config.change` 事件绕开了 ACL 问题。这在当时是对的（避免被 `rc=6` 卡死），但它是绕路：

- 语义不对：uci 是配置，不是命令通道
- 无法返回结构化错误
- 无法区分「谁调的」

正确做法：写 `acl.d/luci-app-dns-switch.json` + rpcd 脚本，一次做对，前端用 `rpc.declare`。v1 的实测已经证明 ACL 是可控的，只是当时没时间。

### 5.3 前端不重绘

v1 有个 bug：每 5 秒无条件重建 DOM。已修（数据不变不重绘），但这是设计问题不是补丁问题——轮询应该只更新变化的部分，或改用长连接/事件。

## 八、一句话总结

v1 解决的是「我怎么切」，v2 要解决的是「**我怎么知道它现在是好的、坏了怎么 90 秒内救回来、以及怎么让别人也能用**」——而且只对自己那一层负责，不越界去假装能修网络服务。

前者是功能，后者是产品。

# v1.0.1

**只修缺陷，不动功能。** 三个都是「用户能看见但实际不影响 DNS 行为」的问题，加上两处文档与实测不符的更正。

v1.0.0 的 46 条真机回归、装/用/卸/重启四项、固件出厂自带链路全部沿用，本版未改任何切换 / 降级 / 对账 / 快照逻辑。

## 修了什么

| 编号 | 现象 | 根因 | 修法 |
|---|---|---|---|
| R-1 | `dns-switch status` 的「ether 豁免: N 条」**恒显示 0** | 数的是磁盘片段 `/etc/nftables.d/20-dns-hijack.nft`，而该文件在规则应用后已不含 ether 行；运行链里实际有 2 条 | 改读 `nft list chain inet fw4 dns_hijack`（内核真实状态） |
| — | 每次 `apk add` 都留下 `/etc/config/dns_switch.apk-new`（703 B） | apk 遇到已存在的 conffile 会写候选文件；该目录又会被 sysupgrade 整份保留，跟着进下一次升级 | postinst 里 `rm -f /etc/config/dns_switch.apk-new` |
| — | 安装时打印 `uci: Parse error (invalid command) at line 5` | apk 安装瞬间 `/etc/config/dns_switch` 处于 copy-up 中间态，uci 解析失败（v1.0.0 被 `\|\| true` 兜住，功能无影响） | postinst 先探测 `uci -q show dns_switch`，最多重试 3 次；仍失败则保留 uci-defaults 给下次开机并记 syslog，不再把错误甩到安装输出里 |

## 文档更正（不影响代码）

- **`apk` 数据库记录丢失**：确认**只在「手动 apk add + sysupgrade」场景发生**。固件出厂自带时记录在 `/rom/lib/apk/db`，2026-11-18 实测升级后 `apk info -e` 正常。
- **重装后 `mode`**：`apk del` 后重装是出厂态 `mode=off`，需手动 `dns-switch on`；只有**覆盖安装**才保持原来的 `on`。旧版运维手册写「装完即 mode=on」不准确。

## 装机

```sh
# 25.12 及以后（apk）
apk add --allow-untrusted luci-app-dns-switch_1.0.1-r1.apk

# 23.05 / 24.10（ipk）
opkg install luci-app-dns-switch_1.0.1-r1.ipk
```

覆盖安装后**必须重启守护**再验证 daemon 行为：

```sh
/etc/init.d/dns-switch restart
dns-switch status           # 「ether 豁免」现在与运行链一致
```

## 未实现（与 v1.0.0 相同，不要期待）

- 上游链抽象（多级探测 / 手动锁定某一级）
- 效果统计（拦截量、平均解析耗时）
- 审计（谁切的、来源 IP）
- ucode 重写 + ubus 对象（仍是 POSIX sh 单文件，`ubus call dns-switch status` 不可用）

## 已知限制

- 仅支持 fw4 / nftables（OpenWrt 22.03+），fw3 上装了不生效
- 需要 busybox 带 `flock` applet
- `curl` 是精度增强不是硬依赖：缺它探测降一档，页面会提示
- 快照回滚会连同 `dns_switch` 参数一起还原（v1.0.0 起的行为）

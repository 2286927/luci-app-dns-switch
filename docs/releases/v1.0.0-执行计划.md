1. **唯一基线**：后续所有任务从本文件的 `W` 编号取。表外需求一律先走变更流程，不得插队。

### W3 · 推送远端

**前置**：W2 DONE。**此步有两条互斥路径，由 OD-4 决定走哪条。**

#### 路径 A（默认，不需要动 token）：网页逐文件上传

```bash
cd D:/我的知识库/OpenWrt编译
./test-run-20261112/push_file.sh \
  "D:/我的知识库/OpenWrt编译/luci-app-dns-switch/luci-app-dns-switch/root/usr/bin/dns-switch" \

  "修 F1/F2/N2：守护重读配置、快照还原参数、rescue 复位生效态"
```

共 **7 次**上传（6 个改动文件 + 新增 workflow），顺序建议：
`usr/bin/dns-switch` → `overview.js` → `acl.d/*.json` → `config/dns_switch` → `README.md` → `build.yml` → `build-apk-25.12.yml`

代价与副作用：
- 远端产生 7 个 commit，历史偏碎
- 文件 **mode 为 644**（网页上传不保留执行位），靠 CI 的 `Restore executable bits` 兜底。**后果**：别人 clone 后不跑 chmod 直接 `make`，打出的包缺执行位
- 中途失败会留下半更新的仓库状态（无生产影响，包不在跑）

#### 路径 B（推荐，需你改一次 token）：升级为 Contents: write

GitHub → Settings → Developer settings → Fine-grained tokens → 该 token → Repository permissions → **Contents: Read and write** → Save。

```bash
git remote add origin https://<token>@github.com/2286927/luci-app-dns-switch.git
git fetch origin
git rebase origin/main          # 吸收远端那批网页提交
git push origin HEAD:main
```

代价与收益：一次性 2 分钟配置，换来**一次推完 + mode 位正确（100755）+ 历史线性**，且以后所有发版都省掉 7 次网页上传。

**判据（两条路径共用）**：
```bash
# 远端 6 个文件的 blob SHA 必须与本地逐一相等
for f in luci-app-dns-switch/root/usr/bin/dns-switch \
         luci-app-dns-switch/htdocs/luci-static/resources/view/dns_switch/overview.js \
         luci-app-dns-switch/root/etc/config/dns_switch \
         luci-app-dns-switch/root/usr/share/rpcd/acl.d/luci-app-dns-switch.json \
         README.md .github/workflows/build.yml; do
  printf "%s\n  本地 %s\n" "$f" "$(git rev-parse HEAD:$f)"
done
# 远端值用 API 取：GET /repos/2286927/luci-app-dns-switch/contents/<path> 的 sha
```
- 主程序远端内容 md5 必须等于 `3ffa3f2a…`
- 路径 B 额外：`git ls-tree -r origin/main | grep 100755` 出现 3 行

**回滚**：路径 A 每个上传都是一个 commit，可在 GitHub 上 revert；路径 B 用 `git revert`。

**风险**：

| 风险 | 等级 | 对策 |
|---|---|---|
| 网页上传中途失败（bsk 会话失效 / 页面改版） | 中 | 脚本已有 5 段检查点与退出码；失败就从断点文件继续，不重传已成功的 |

| 误把 token 推入提交 | 低 | F12 已核：历史无敏感文件；`.gitignore` 无需改（token 文件在仓库外） |

### W5 · 真机复验（D4）

**前置**：W4 DONE；设备在线。

**前置检查（先过这三条再动手）**：
```bash
ping -c 2 172.16.1.1                       # R68S 可达
ssh root@172.16.1.1 'uci get dns_switch.settings.adh_ip'   # = 172.16.1.2
ssh root@172.16.1.2 'wget -qO- http://127.0.0.1:3030/ | head -1'  # ADH 在线
```

**动作**：

```bash
# 1) 备份现场
ssh root@172.16.1.1 'uci export dns_switch > /tmp/ds.bak; uci export dhcp > /tmp/dhcp.bak'

# 2) 装新包（noarch，可与旧版覆盖）
scp new.apk root@172.16.1.1:/tmp/
ssh root@172.16.1.1 'apk add --allow-untrusted --force-overwrite /tmp/new.apk'

# 3) 确认装的是验收版
ssh root@172.16.1.1 'md5sum /usr/bin/dns-switch'     # 必须 = 3ffa3f2a…

# 4) F1 回归（本轮唯一必须复跑的缺陷验证）
python test-run-20261111/exp_f1.py                    # 约 40 秒

# 5) 冒烟：四个方向
ssh root@172.16.1.1 'dns-switch status | head -6; dns-switch off; dns-switch on; dns-switch drill'
```

**判据**：
- `exp_f1.py` 输出 `修复后 opt6 = 6,172.16.1.2,172.16.9.9`，`applied_sig` 含 `9.9`
- `dns-switch status`：`mode=on`、`effective=on`、`53 端口: 正常`、`劫持链: 在位`
- `drill` 返回 0，终态仍为 `on`
- 解析实测：`nslookup www.baidu.com 172.16.1.1` 有 Address

**回滚**：
```bash
ssh root@172.16.1.1 'dns-switch rescue; apk add --allow-untrusted --force-overwrite /tmp/old.apk'
# 或直接 uci import 回 /tmp/ds.bak + /tmp/dhcp.bak
```
设备侧永远有 `dns-switch rescue` 这条不依赖任何东西的退路。

**风险**：真机操作不可逆性最高。**必须保住 SSH 会话不断**（dropbear 走 IP，不经 DNS），必要时先挂 5 分钟看门狗：
```bash
ssh root@172.16.1.1 '( sleep 300; /usr/bin/dns-switch off ) &'
```

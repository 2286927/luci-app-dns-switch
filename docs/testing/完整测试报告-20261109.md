## 测试中发现的产品缺陷（已修）

**快照回滚会让 mode 与 DHCP 下发错位。**

快照是在 `on`/`off` 动手之前拍的。如果在「关闭态」拍到，快照里的 `dhcp` 没有 `option6`；回滚时把 `mode` 恢复成 `on`、配置却还是空的，结果就是 **`mode=on` 但客户端拿不到任何 DNS 下发**，而界面和 `status` 都显示正常。

测试末段核对最终状态时发现 `option6=[]`、`RDNSS=[]` 而 `mode=on`，才暴露出来。

修法：回滚完成后，若 `mode=on` 就再跑一次 `do_on`，按当前参数重新下发，保证配置与意图一致。修后复测：回滚结束 `option6=6,172.16.1.2,172.16.5.5`、`RDNSS=fdc7:c520:79f1::2`、`mode=on`。

## 测试侧修掉的三处缺陷

1. **闸门用例断言写错**：拿「mode 应回退到 off」当预期，但测试开始时 mode 本就是 on，回退到 on 才对。改为比对前后一致。
2. **快照用例行号解析错**：表头占了列表第一行。
3. **保存用例的填值方式错**：直接赋 `element.value` 不触发 CBI 监听的 input 事件，表单数据没更新；改用 bsk 的 fill（会派发事件）后再点保存即成功。

## 工具限制（非产品问题）

- bsk 的点击坐标比元素实际位置低约 82px，指针点击必然落空，必须用页面内 `element.click()`。
- `cooperate sync` 在一次会话中只前两三次有效，之后返回缺 observation 的错误对象。对策：每用例独立会话，或把多步操作压进单次 evaluate。

## 断言自身暴露的两个缺陷（已修，属本轮最有价值的发现）

**一、CRLF 检测用 `grep` 在 Windows 上永远查不出来。**
MSYS/MinGW 的 grep 是文本模式，把 `\r\n` 当 `\n`，`grep -c $'\r'` 对一份明显 CRLF 的文件返回 0。改走 `od -An -c` 的字节视图。

**二、`grep -q` 在 `pipefail` 下把成功判成失败。**
`od | grep -q` 命中即退，od 收 SIGPIPE 返回 141，`pipefail` 让整条管道判失败——结果 CRLF 文件反而显示"干净"。改用 `grep -c`。

这两条都是"断言看起来在工作、其实永不报警"的典型。发现方式是把 9 份坏固件逐条喂给 verify.sh，看它会不会红。

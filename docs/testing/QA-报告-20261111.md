## C. F6 —— 缺 curl 不得阻断、更不得把全网降级

### C.1 第 1 轮：**失败**（1593e777）

现场复现步骤与结果：

1. `mv /usr/bin/curl /tmp/curl.qa.bak`（不动 apk 记录）；
2. 新 SSH 会话 `dns-switch status` → 文案正确："探测依赖: 缺 curl（仅按 DNS 探测）…"，`status.dep=no-curl`；
3. `dns-switch on` → rc=0（闸门没拦），option6 正常；
4. 但**常驻 daemon 的下一轮 tick 把 dep 写回 `ok`**（实测 +20s），随后 `probe_adh` 走 curl 分支 → curl 不存在 → http_code 空 → 判 ADH 不可用 → 连续 2 次失败后自动降级：
   ```
   17:19:25 DHCP 下发 DNS → 6,172.16.1.1
   17:19:27 ADH 不可用，已降级到运营商 DNS
   ```
   `effective` 由 on → **failover**，option6 变 `6,172.16.1.1`；盯到 +190s 仍未自愈。

**根因**：`have_curl()` 用 `command -v curl` 判断，而 BusyBox ash 会缓存命令查找结果。真机最小复现：
```
$ /bin/sh -c 'curl --version >/dev/null 2>&1; echo used=$?; mv /usr/bin/curl /tmp/curl.exp; command -v curl; echo cv_rc=$?; curl --version; echo exec_rc=$?'
used=0
/usr/bin/curl
cv_rc=0
exec_rc=127
```
daemon 恰好是"同一个 shell 里每轮都执行 curl"的进程，hash 里永远有 `/usr/bin/curl`；用户 `apk del curl` 之后守护仍认为有 curl → 探活恒失败 → 降级。新开的 SSH 会话没有 hash，所以命令行说 no-curl、后台说 ok。

→ 已返工工程师（建议：`command -v` 结果再过 `-x`）。

### C.2 第 2 轮：**通过**（c637eb9a）

## I. ACL 缺失实验（发布缺口定性：体验退化 还是 出厂即坏）

**实验设计**：`mv /usr/share/rpcd/acl.d/luci-app-dns-switch.json` → `/etc/init.d/rpcd restart`（清会话）→ 重新登录 → 看页面渲染 / `uci.load` / `fs.stat`；随后 `try/finally` 恢复 ACL 并复验。

|---|---|---|---|---|
| I1 | 移除 app ACL + rpcd restart + 重新登录，打开页面 | 页面渲染 / uci 读 / fs.stat 三项结果 | 页面 **5s 渲染完成**（size=18724，无"加载视图中"）；`uci.load('dns_switch')` → `OK mode=on dep=ok effective=on`；`fs.stat('/usr/bin/curl')` → `OK {"type":"file","size":163953,…}`（**不是** Permission denied） | 见结论 |

| I3 | 根因取证：root 会话到底拿到了什么 ACL | — | `session.login` 返回的 `acls` 里有 **`uci: ['*', …]`** 与 **`file: ['/*', …]`**，外加 `access-group.allow-full-uci-access` | 见结论 |

**结论（与预先假设相反，必须更正）**：

- **缺 ACL 在本机（仅 root 账号）没有功能影响**：页面能渲染、能读 `dns_switch`、`fs.stat` 也能成功。原因是 **root 登录时 rpcd 给它的是全量 ACL**（`uci:"*"`、`file:"/*"`），app 那份 ACL 对 root 是**冗余**的。
- 所以 F8（factory payload 不带 `acl.d/luci-app-dns-switch.json`）**不是"出厂即坏"**，也不会让"刷新即消失"退化——这一点与实验前的推测不一致，以实测为准。
- **影响面边界**：本次要发布的 **apk/ipk 包内是带 ACL 的**（`root/usr/share/rpcd/acl.d/luci-app-dns-switch.json` 在包内），所以包发布路径完全不受影响；本条只针对 **factory 出厂固化 payload**（恰好 6 个运行时文件，不含 ACL）。
- 但它是**真实的打包不一致**：app ACL 只对**非 root 的 LuCI 账号**有意义（多用户 / 受限账号场景）。
- **F8 的非 root 场景「未实测」**：依据是 ACL 结构（`luci-base.json` 只给 `uci: ["system","luci"]`、`file: {"/": ["list"], "/*": ["list"]}`，既没有 `*` 也没有 `stat`）与 root 全量授权的对照。**没有构造真实的非 root 账号去验证**——造账号要改 `/etc/config/rpcd`，改坏有把自己锁在门外的代价；而该项不阻塞本次发布，且不论届时报的是 `Permission denied` 还是 `Access denied`，改法都只有一条「把 ACL 放进 payload」，证据链不会改变动作。下一版真正处理 F8 时，用真实非 root 账号验一次再定措辞。
- 建议下一版把 ACL 打进 payload（成本几乎为零），**但不作为本次发布的阻塞项**。
